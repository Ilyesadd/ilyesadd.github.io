Contexte

Ce Pokédex Interactif est un projet personnel réalisé durant mon année de BTS SIO SLAM à l'INSTA Paris. L'objectif était de consolider mes compétences en PHP côté serveur en travaillant avec une API REST externe, sans recours à un framework — uniquement du PHP natif, HTML et CSS.

Le projet consiste en une application monopage qui interroge l'API publique PokéBuild FR via file_get_contents() pour récupérer les données de chaque Pokémon en temps réel, puis les affiche dynamiquement. La recherche accepte aussi bien le nom français que le numéro du Pokédex.

Ce qui rend le projet visuellement mémorable : le thème couleur de toute la page (dégradé du fond, couleur du titre, des badges) change dynamiquement en fonction du type principal du Pokémon affiché — Feu → orange, Eau → bleu, Électrik → jaune, etc.

03

Fonctionnalités réalisées

—
Consommation d'API REST externe
Appel à l'API PokéBuild FR via file_get_contents() avec gestion du contexte HTTP, timeout à 5 secondes et vérification du code de réponse. Décodage du JSON retourné pour extraire les données utiles.
—
Affichage dynamique des statistiques
Affichage de : Numéro Pokédex, Nom, Types, PV, Attaque, Défense, Vitesse, Génération et sprite officiel. Toutes les données sont extraites de la réponse JSON de l'API.
—
Thème couleur adaptatif par type
Chaque type (Feu, Eau, Plante, Électrik, Psy, Dragon…) est associé à une paire de couleurs définie côté PHP. Le dégradé CSS, le titre et les badges sont générés dynamiquement à partir de ces variables — changement instantané à chaque recherche.
—
Recherche par nom ou par numéro
Le formulaire accepte le nom français du Pokémon (ex : Bulbizarre) ou son numéro Pokédex (ex : 25). L'URL est encodée via urlencode() avant l'appel API.
—
Suggestions de Pokémon populaires
Raccourcis cliquables sous le formulaire (Pikachu, Bulbizarre, Salamèche, Carapuce, Mewtwo, Évoli, Ectoplasma, Ronflex) pour naviguer rapidement sans taper.
04

Sécurité & Bonnes pratiques

01
Protection XSS
Toutes les données affichées (nom du Pokémon, query de l'utilisateur) passent par htmlspecialchars() pour neutraliser toute injection HTML ou JavaScript.
02
Gestion des erreurs HTTP
Vérification du header de réponse HTTP ($http_response_header) — si l'API retourne une erreur 404 ou 500, un message d'erreur explicite est affiché sans exposer les détails techniques.
03
Encodage des URL
La saisie utilisateur est encodée avec urlencode() avant d'être insérée dans l'URL d'appel à l'API, empêchant toute manipulation de l'URL.
04
Timeout de requête
Un timeout de 5 secondes est configuré via le contexte HTTP. En cas de non-réponse de l'API, l'application affiche un message d'erreur et ne reste pas bloquée.
